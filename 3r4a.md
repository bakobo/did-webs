# Nothing bounds the submitted CESR stream before keripy parses it
kind: todo
created: 2026-09-15T04:17Z

- 2026-09-15T04:17Z dev/standards/input-handling.md: nothing crosses a boundary unbounded, size before shape before meaning. cli.py:79-80 reads the whole submitted stream with file.read() and hands it to ingest.ingest(), which takes bytes and walks every frame. There is no size cap, no frame-count cap, and no per-frame cap anywhere in the repo -- grep for MAX_/limit finds only did.py's RFC 1035 host and label lengths. That is the standard's named anti-pattern: verifying every signature in a stream of unbounded length is a more expensive way to run out of memory, and none of the semantic rigour in ingest.py starts until the bytes are already resident.

NOT urgent today, and the reason is worth keeping straight. Phase 1 is a local operator command, so the operator chose the file; cli.py's own docstring already says the pipeline establishes no submitter-to-AID binding and none of this is network-facing. This debt belongs in the same sentence as that one: both must land BEFORE any submission surface exists. A submission endpoint with no bound is a memory exhaustion an unauthenticated caller can trigger.

Shape when it is paid: a door per input kind that reads limit+1 bytes and refuses on the overage rather than reading the file and measuring it, plus a census test (AST walk over boundary primitives, each call site a door or an argued exemption) so a later unguarded read fails at authoring time. bakobo/did-webvh implemented exactly this on 2026-09-15 -- src/didwebvh/bounds.py and tests/test_doors.py are a working reference, and the numbers there are flood guards rather than capacity planning. Found while building the sibling repo, not in a review of this one.
