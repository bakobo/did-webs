Sharpened the mechanism beyond what this tick said. The damage is not the missing escrow entry -- it is that escrowLDEvent raises AttributeError, and BOTH call sites (eventing.py:4352 and :4437) raise LikelyDuplicitousError on the line AFTER the call. So the typed error is never raised at all, the Parser's broad except arm swallows the AttributeError and resumes, and a likely-duplicitous event is neither escrowed nor reported. Silence in both directions, which reads as 'no duplicity found'.

Root cause is a migration leftover: ldes exists and is healthy (basing.py:1002, an OnIoDupSuber with .add(keys=, on=, val=)); the caller still uses the pre-subing addLde(snKey(...), val) signature. Suggested fix in the draft is the one-line OnIoDupSuber form.

Demonstrated live: forked_kel fixture -> 0 ldes entries, hasattr(db,'addLde') False, and didwebs' own same-sn scan still catches the fork. The 3vol note says bakobo/stack carries a fix (0327e69b) -- that is OUR fork; upstream does not have it.
